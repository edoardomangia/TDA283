# TDA283

## Introduction

This repository contains a compiler for Javalette, a small imperative language with a BNFC-based front end, semantic analysis, and code generation.
The base language contains functions, local variables, blocks, conditionals, while loops, returns, scalar types, arithmetic, comparisons, boolean operators, function calls, and the provided primitive I/O functions.

The compiler is written in C++ 17, implementing:

- The base language.
- 2 array extensions.
- 2 backends:
  - `jlc`, emits LLVM IR on standard output.
  - `jlc_riscv`, emits RV64 RISC-V assembly on standard output.

The lexer, parser, AST classes, printer, and skeleton visitor are generated from `src/Javalette.cf` by BNFC, Flex, and Bison. The more interesting parts are the type checker, the LLVM code generator, and the RISC-V code generator.

## How the compiler works

### From grammar to parser

The compiler starts from `src/Javalette.cf`. This file is the BNFC grammar for the implemented Javalette language.
It describes the abstract syntax, concrete syntax, token-level comments, expression precedence, and list syntax in one place.

The first important declaration is:

```bnf
entrypoints Prog ;
Program. Prog ::= [TopDef] ;
```

This tells BNFC that a complete source file is parsed as a `Prog`, and that the concrete top-level program node is named `Program`. Other labelled productions work the same way. For example:

```bnf
FnDef. TopDef ::= Type Ident "(" [Arg] ")" Blk ;
Decl.  Stmt   ::= Type [Item] ";" ;
EAdd.  Expr3  ::= Expr3 AddOp Expr4 ;
```

BNFC turns these labels into C++ AST classes such as `Program`, `FnDef`, `Decl`, and `EAdd` in `src/Absyn.H` and `src/Absyn.C`.

The fields of those classes come directly from the right-hand side of the grammar rule. A `FnDef`, for example, contains a return `Type *`, an `Ident`, a `ListArg *`, and a `Blk *`.

The grammar also explains expression precedence through the numbered expression categories.

- Atomic expressions are at `Expr6`.
- Unary operators at `Expr5`.
- Multiplication at `Expr4`.
- Addition at `Expr3`.
- Comparisons at `Expr2`
- `&&` at `Expr1`
- `||` at `Expr`.

The rule:

```bnf
coercions Expr 6 ;
```

lets BNFC insert the coercion rules that move expressions between these levels, so parentheses and precedence are handled by the generated parser rather than by handwritten compiler code.

BNFC list declarations such as:

```bnf
separator Arg "," ;
separator Stmt "" ;
```

generate list classes such as `ListArg` and `ListStmt`. They are used throughout the AST when a node contains zero or more arguments, statements, top-level definitions, or expressions. The `comment` declarations generate lexer rules for `#`, `//`, and `/* ... */` comments.

The `Makefile` connects this grammar to the build. When generated frontend files are missing or older than `src/Javalette.cf`, it runs:

```sh
./src/bnfc --cpp -o src src/Javalette.cf
```

This produces:

- The C++ abstract syntax files
- a Bison grammar `src/Javalette.y`
- a Flex lexer specification `src/Javalette.l`
- a parser interface
- a printer
- a skeleton visitor.

Flex then turns `src/Javalette.l` into `src/Lexer.C`; Bison turns `src/Javalette.y` into `src/Parser.C` and `src/Bison.H`; and the normal C++ build compiles those files together with the handwritten compiler phases.

### Parsing and driver control flow

The main LLVM executable is implemented in `src/main.cpp`. The RISC-V executable
in `src/main_riscv.cpp` has the same frontend flow. The driver accepts either
one source filename or no filename. With a filename it opens that file; without
one it reads from standard input.

After opening the input, the driver calls:

```cpp
Prog *prog = pProg(input);
```

`pProg` is the parser entry point generated by BNFC and declared in `src/Parser.H`. Internally, it uses the generated lexer and Bison parser to read
tokens and build the generated C++ AST. If lexing or parsing fails, the generated
parser reports a `parse_error`; the driver catches it, prints `ERROR` on the
first stderr line, prints the parse diagnostic, and exits with a non-zero status.

If parsing succeeds, the result is a `Prog *`. In practice, because the grammar
has `Program. Prog ::= [TopDef]`, the object is a `Program *` containing a
`ListTopDef *`. Each top-level definition is a `FnDef *`, and each function
contains its return type, name, parameter list, and block AST.

The driver does not generate code immediately after parsing. It first constructs
the handwritten type checker:

```cpp
TypeChecker tc;
tc.checkProgram(prog);
```

Only if `checkProgram` returns normally is the AST considered semantically
valid. If it throws `TypeError`, the driver prints `ERROR`, then a type-error
message, and exits without producing a successful compilation.

### Type checker

The type checker is implemented in `src/TypeChecker.H` and `src/TypeChecker.C`.

It inherits from the BNFC-generated `Skeleton` visitor, which itself implements the generated `Visitor` interface from `src/Absyn.H`.

This lets the checker traverse the AST by calling each node's generated `accept` method, while overriding only the node kinds that have semantic rules.

The generated parser is therefore responsible for syntactic structure, and the handwritten checker is responsible for declarations, scopes, expression types, function calls, returns, and array-specific rules.

The checker reports semantic failure by throwing `TypeError`. The driver catches that exception, prints `ERROR` as the first line of standard error, and skips code generation. If `checkProgram` returns normally, the rest of the compiler treats the AST as well typed.

#### Semantic type model

The checker does not use the raw BNFC `Type *` nodes as its internal type representation. It converts them to a compact semantic type:

```cpp
enum class PrimType { INT, DOUBLE, BOOL, VOID };

struct SemType {
  PrimType base;
  int arrayDepth;
};
```

The `base` field stores the scalar element kind, and `arrayDepth` stores how many array layers surround it. For example:

- `int` is `{INT, 0}`;
- `double[]` is `{DOUBLE, 1}`;
- `boolean[][]` is `{BOOL, 2}`.

This representation makes scalar and array checks uniform.

A type is an array exactly when `arrayDepth > 0`, and indexing an array is implemented by reducing the depth by one.

The helper `fromAstType` converts declared types such as `int`, `void`, and `int[][]` into `SemType`.

The helper `fromAstBaseType` converts the restricted base types used by `new`, where the grammar allows only `int`, `double`, and `boolean` as array element bases.

Arrays of `void` and plain variables of type `void` are rejected during this conversion or during declaration checking.

Function types are represented separately:

```cpp
struct FunType {
  SemType result;
  std::vector<SemType> args;
};
```

The function environment maps function names to these signatures:

```cpp
std::map<std::string, FunType> funEnv;
```

#### Program-level passes

`checkProgram` performs two passes over the top-level definitions.

The first pass builds `funEnv`. Before inspecting user-defined functions, it installs the primitive functions that have ordinary Javalette types:

- `printInt : void(int)`
- `printDouble : void(double)`
- `readInt : int()`
- `readDouble : double()`

`printString` is checked as a special case instead of being stored as an ordinary typed function, because this compiler does not have a first-class `string` type.

String literals are accepted only as direct arguments to `printString`.

While building the function environment, the checker also verifies that every
top-level definition is a function, rejects duplicate function names, rejects
duplicate parameter names inside the same function, rejects parameters of type
`void`, and checks that the required entry point exists with exactly the type
`int main()`.

The second pass checks each function body.

For the function currently being checked, the checker stores the expected return type in `currentFunResult`, pushes a variable scope for the parameters, binds each parameter as a local variable, and then visits the function block. After the block has been visited, non-`void` functions are checked for a statically evident return path.

The return-path check is intentionally simple. A statement is considered returning if it is a `return`, a block that contains a returning statement, or an `if-else` where both branches are returning. A plain `if` without `else` and a `while` loop are not considered guaranteed returns, even if their condition is obviously constant. The checker does not try to prove reachability or evaluate constant conditions.

#### Variable scopes

Local variables are stored in a stack of scopes:

```cpp
std::vector<std::map<std::string, SemType>> varStack;
```

Entering a block pushes a new map; leaving the block pops it.
Lookup searches from the innermost map outward, so variables in inner blocks can shadow variables from outer blocks. Redeclaring a name in the same block is rejected.

Function names and variable names are kept distinct. If an identifier is used as
a variable and no local binding exists, the checker reports a specific error
when that identifier is actually a function. Conversely, a call expression is
rejected if the called name is currently bound as a local variable. This avoids
silently treating a variable as a function or a function as a value.

#### Statement checking

Each relevant statement node has a visitor method with the local rule for that
statement form:

- declarations reject `void` variables, check each initializer expression, and
  bind the declared names in the current scope;
- assignments use `checkLhs` to compute the type of either a variable target or
  an indexed array target, then require the right-hand expression to have the
  same type;
- `++` and `--` require an assignable left-hand side of type `int`;
- `return expr;` is legal only in non-`void` functions and must match the
  enclosing function result type exactly;
- `return;` is legal only in `void` functions;
- `if`, `if-else`, and `while` conditions must have scalar type `boolean`;
- `for (T x : arr)` requires `arr` to be an array and `T` to match its element:E
  type exactly;
- expression statements are accepted only when the expression has type `void`,
  which makes calls such as `printInt(x);` legal while rejecting statements such
  as `x + 1;`.

The checker does not insert implicit conversions. For example, assigning an
`int` to a `double`, passing a `double` where an `int` is expected, or mixing
`int` and `double` in an arithmetic expression is rejected.

#### Expression checking

Expression visitors compute the type of the expression currently being visited
and store it in `currentExprType`. Parent visitors save that value when they
need to compare the types of multiple subexpressions.

Literal and variable expressions are the base cases. Integer, double, and
boolean literals set `currentExprType` to the corresponding scalar type.
Variable expressions look up the identifier in `varStack`. String literals are
not treated as normal values; the visitor uses a placeholder `void` type, and
the call checker accepts them only in the special `printString` case.

Function calls are checked against `funEnv`. The checker first rejects calls
where the name is shadowed by a local variable. It then checks that the function
exists, that the number of actual arguments matches the signature, and that
each actual argument has exactly the expected semantic type. The expression type
of a successful call is the function result type.

Unary and binary operators enforce the Javalette typing rules:

- unary `-` accepts scalar `int` or `double` and keeps the operand type;
- unary `!` accepts scalar `boolean` and produces `boolean`;
- `*`, `/`, `+`, and `-` require both operands to have the same scalar numeric
  type and produce that type;
- `%` requires two scalar `int` operands and produces `int`;
- `==` and `!=` require matching non-array, non-`void` scalar operands and
  produce `boolean`;
- `<`, `<=`, `>`, and `>=` require matching scalar numeric operands and produce
  `boolean`;
- `&&` and `||` require scalar `boolean` operands and produce `boolean`.

#### Array checking

Arrays are checked through the same `SemType` representation. `new` expressions
use a base type plus one or more dimension expressions. Every dimension
expression must have type `int`, and the resulting type has the selected base
and a depth equal to the number of dimensions. For example, `new int[n][m]`
has type `int[][]`.

Indexing first checks that the indexed expression has array type, then checks
that the index expression has type `int`. The result type is the element type,
so indexing `int[][]` once gives `int[]`, and indexing it twice gives `int`.
Indexed assignment uses the same logic through `checkLhs`, but returns the
element type as the assignable target type.

The `.length` attribute is accepted only on arrays and only with the exact
attribute name `length`. Its result type is always `int`. Foreach loops use the
same element-type helper: the loop expression must be an array, and the declared
loop-variable type must exactly match the array element type.

#### Relationship to code generation

The type checker validates the AST but does not rewrite it and does not attach
type annotations to AST nodes. Later phases still perform their own simple
AST-to-codegen type conversion, but they rely on the checker for semantic
guarantees: function calls have the right arity and argument types, assignments
are type-correct, conditions are boolean, return statements match their
function, and array operations are applied only to array values with integer
indices.

### LLVM backend

The main compiler executable `jlc` calls:

```cpp
generateLLVM(ast, std::cout);
```

after the AST has passed type checking. The LLVM backend is implemented in
`src/CodeGenLLVM.cpp`. It does not use the LLVM C++ API. Instead, it emits
textual LLVM IR directly to the output stream.

#### LLVM generation order

The top-level entry point is `generateLLVM`. It creates a `CodeGen` object and
calls its `gen` method. Generation then happens in three main phases.

First, `emitPrelude` emits external declarations for the runtime functions:

- `printInt`
- `printDouble`
- `printString`
- `readInt`
- `readDouble`
- `calloc`

Second, the backend walks over the top-level function definitions and records
their result types in `fnSigs`. This signature pass is needed because
Javalette allows a function to call another function that appears later in the
source file.

Third, the backend emits each function body. The final output order is:

```text
runtime declarations
array type declarations and global constants
function definitions
```

The LLVM backend has a code-generation type model `CGType`, similar to the type
checker `SemType`:

```cpp
struct CGType {
  CGBase base;
  int arrayDepth;
};
```

The `base` field stores the scalar element type, and `arrayDepth` stores how
many array layers surround it. Scalar Javalette types are mapped as follows:

- `int` to `i32`
- `double` to `double`
- `boolean` to `i1`
- `void` to `void`
- string literals to `i8*` when passed to `printString`

Array types are represented as pointers to generated LLVM structure types. For
example, `int[]` uses:

```llvm
%arr_int_1 = type { i32, [0 x i32] }
```

and values of that type have LLVM type `%arr_int_1*`. The first field stores
the array length. The second field is a flexible zero-length element area used
with `getelementptr`. For multidimensional arrays, the element type is another
array pointer, so `int[][]` is represented as an array whose elements are
`%arr_int_1*`.

#### Functions, locals, and values

Each Javalette function is emitted as one LLVM function:

```llvm
define <result-type> @functionName(<parameters>) {
entry:
  ...
}
```

Parameters arrive as LLVM SSA values. At function entry, the backend allocates
a stack slot for each parameter, stores the incoming value into that slot, and
binds the source-level parameter name to the slot. Local variables are handled
the same way: every declared variable gets an `alloca`.

This means mutable Javalette variables are represented by memory locations
rather than by pure LLVM SSA variables. A declaration such as:

```java
int x = 3;
```

is emitted in the same style as:

```llvm
%t0 = alloca i32
store i32 3, i32* %t0
```

A later use of `x` emits a `load`, and an assignment emits a `store` back into
the same slot. The backend keeps a stack of variable scopes, where each name is
mapped to the LLVM pointer and its `CGType`.

Expression generation returns an `RVal`:

```cpp
struct RVal {
  std::string v;
  CGType ty;
  std::string blk;
};
```

The `v` field is the LLVM operand name or literal value, `ty` is the generated
type, and `blk` is used when boolean expressions create their own basic blocks.

#### Expression generation

Literal expressions are emitted directly as LLVM constants: integer literals as
`i32` values, double literals as `double` values, and booleans as `0` or `1`.
Variable expressions look up the variable slot and emit a `load`.

Arithmetic expressions recursively generate the left and right operands and
then emit the matching LLVM instruction:

- integer arithmetic uses `add`, `sub`, `mul`, `sdiv`, and `srem`;
- double arithmetic uses `fadd`, `fsub`, `fmul`, and `fdiv`.

Comparison expressions use `icmp` for integer, boolean, and pointer-like
values, and `fcmp` for doubles. The result of every comparison is `i1`.

Function calls first generate all argument expressions. Primitive calls are
emitted directly against the runtime declarations. User-defined calls use the
function return type saved during the signature pass. A non-void call produces
a fresh temporary:

```llvm
%t5 = call i32 @f(i32 %t4)
```

while a void call is emitted without assigning its result.

Short-circuit boolean expressions are generated with basic blocks, branches,
and `phi` nodes. For `a && b`, the backend first generates `a`. If `a` is
false, control jumps directly to the result block with value `false`. If `a` is
true, it generates `b` and uses the value of `b` as the result. `a || b` is
handled symmetrically: if `a` is true, the result is immediately true, and `b`
is generated only on the false path.

#### Statement generation

Statements are emitted by `genStmt`.

Declarations allocate stack slots and store either an initializer value or a
default value. The default scalar values are `0`, `0.0`, and `false`. The
default value for an array variable is a generated empty-array global of the
corresponding array type.

Assignments first generate an assignable reference with `genLhs`. A plain
variable left-hand side returns the variable slot. An indexed left-hand side
generates a pointer to the selected array element. The right-hand expression is
then generated and stored into that pointer.

`++` and `--` are emitted as a load from the assignable reference, an integer
`add` or `sub`, and a store back to the same reference.

Control flow is emitted with explicit labels and branches. `if`, `if-else`, and
`while` become LLVM basic blocks connected by `br` instructions. Short-circuit
`&&` and `||` are generated with conditional branches and `phi` nodes so the
right-hand expression is evaluated only when the language semantics require it.

The backend tracks whether the current basic block has already been terminated
by a `return`. This avoids emitting extra branches after a block that has
already ended. If a `void` function reaches the end without an explicit return,
the backend emits `ret void`. Non-void functions are expected to have a valid
return path because the type checker has already enforced that.

Foreach loops are lowered into ordinary index-based loops. The backend creates
an integer index slot, compares it against the array length, loads the current
array element into a loop-variable slot, emits the loop body, increments the
index, and branches back to the loop condition.

#### Arrays and strings

Arrays are represented as heap pointers to generated LLVM structure types. For
an array type, the structure contains a 32-bit length followed by a flexible
zero-length element area:

```llvm
%arr_int_1 = type { i32, [0 x i32] }
```

For multidimensional arrays, the element type is another array pointer. Array
creation calls `calloc`, stores the length at offset 0, and, for nested arrays,
generates a loop that allocates each child array. Indexing computes the element
address with `getelementptr`; `.length` loads the first field of the array
structure. The backend does not generate bounds checks.

String literals are interned as private global constants, and each
`printString` call passes a pointer to the first character of the corresponding
global string.

The generated LLVM IR is intended to be linked with `lib/runtime.ll` or
`lib/runtime.bc`, which provide the primitive I/O functions declared in the
prelude.

### RISC-V backend

The optional `jlc_riscv` executable uses the same parser and type checker, then
calls:

```cpp
generateRISCV(ast, std::cout);
```

The RISC-V backend is implemented in `src/CodeGenRISCV.cpp` and emits RV64
assembly. It is a separate backend, but it follows the same source-language
semantics as the LLVM backend.

Values are produced in fixed result registers while an expression is being
generated: integer, boolean, pointer, and array results use `t0`; double results
use `ft0`. When an expression needs to preserve an earlier result while
generating a later subexpression, the backend spills the earlier result into the
current function's stack frame.

Each function has a generated stack frame. The prologue saves `ra` and `s0`,
sets `s0` as the frame pointer, and reserves space for locals and temporaries.
The epilogue restores the saved registers, releases the frame, and returns.
Function parameters are read according to the RISC-V calling convention:
integer-like values use `a0` through `a7`, doubles use `fa0` through `fa7`, and
overflow arguments are loaded from the caller's stack area. Calls are generated
with the same convention in reverse.

The RISC-V backend stores every local variable in the stack frame. Scalar
integer and boolean values use word loads and stores, doubles use floating-point
loads and stores, and arrays and strings are pointers. Arithmetic and comparison
nodes emit the matching integer or floating-point instructions. Boolean
short-circuiting is implemented with labels and conditional branches.

Arrays use the same logical memory layout as the LLVM backend: a length word at
offset 0 and elements beginning after an 8-byte header. Array allocation calls
`calloc`, writes the length, and recursively allocates nested arrays for
multidimensional `new` expressions. Foreach loops are lowered to an index-based
loop over that length field.

String literals and double constants are emitted into read-only data sections.
Uninitialized array variables point at generated empty-array objects. The
backend relies on `lib/runtime-riscv.s` for primitive I/O and on the C library
for `calloc` when linked with the RISC-V cross compiler.

### Runtime and compiler result protocol

The generated programs call a small runtime for primitive I/O. For LLVM, the
runtime is provided as `lib/runtime.ll` and `lib/runtime.bc`. For RISC-V, it is
provided by `lib/runtime-riscv.s`.

The compiler itself follows the protocol expected by the course tester. A
successful compilation writes generated code to standard output, writes exactly
`OK` as the first line of standard error, and exits with status 0. A failed
compilation writes exactly `ERROR` as the first line of standard error, writes a
diagnostic when available, and exits with a non-zero status. This is why parser,
type-checker, and internal exceptions are caught in the driver rather than
being allowed to print arbitrary C++ exception text.

## Building

Run:

```sh
make
```

This builds `jlc` in the repository root. If `riscv64-unknown-linux-gnu-gcc`
is available, `make` also builds `jlc_riscv` and `lib/runtime-riscv.o`.
The RISC-V compiler can also be selected with:

```sh
make RISCV_GCC=/path/to/riscv64-unknown-linux-gnu-gcc
```

Clean generated object files and executables with:

```sh
make clean
```

`make distclean` additionally removes files generated by BNFC, Flex, and
Bison.

## Usage

Compile a Javalette source file to LLVM IR:

```sh
./jlc program.jl > program.ll
```

If no input file is given, `jlc` reads the program from standard input:

```sh
./jlc < program.jl > program.ll
```

On success the compiler prints `OK` to standard error and exits with status 0.
On a lexical, parse, type, or internal error it prints `ERROR` to standard
error, follows it with a diagnostic message when available, and exits with a
non-zero status.

The LLVM output declares the primitive runtime functions and is intended to be
assembled and linked with `lib/runtime.bc` or `lib/runtime.ll`. A typical run is:

```sh
./jlc program.jl > program.ll
llvm-as program.ll -o program.bc
llvm-link program.bc lib/runtime.bc -o program-linked.bc
lli program-linked.bc
```

For the RISC-V backend, when available:

```sh
./jlc_riscv program.jl > program.s
riscv64-unknown-linux-gnu-gcc program.s lib/runtime-riscv.o -o program
```

## Source language

The accepted syntax is specified by `src/Javalette.cf`. The compiler supports:

- top-level function definitions with arbitrary order and mutual recursion;
- required `int main()` entry point;
- scalar types `int`, `double`, `boolean`, and `void`;
- one-dimensional and multidimensional arrays over `int`, `double`, and
  `boolean`;
- function parameters and return values of scalar and array types;
- blocks, empty statements, declarations, assignments, increments,
  decrements, returns, if statements, if-else statements, while loops,
  foreach loops over arrays, and expression statements for `void` calls;
- integer, double, boolean, and string literals;
- arithmetic operators `+`, `-`, `*`, `/`, and integer-only `%`;
- relational operators `==`, `!=`, `<`, `<=`, `>`, and `>=`;
- lazy boolean operators `&&` and `||`;
- unary `-` and `!`;
- function calls;
- array allocation with `new`, indexing, indexed assignment, and `.length`;
- primitive I/O functions `printInt`, `printDouble`, `printString`,
  `readInt`, and `readDouble`.

Strings are not first-class values in this compiler. A string literal is only
accepted as the direct argument to `printString`.

## Type checking

The type checker performs these semantic checks:

- no duplicate function names;
- `main` must have type `int main()`;
- parameter names must be unique inside a function;
- variables and parameters cannot have type `void`;
- arrays of `void` are rejected;
- a variable can be declared only once in the same block;
- inner scopes may shadow variables from outer scopes;
- variables must be declared before use;
- functions and variables are kept distinct, including shadowing cases;
- all non-void functions must contain a statically evident return path;
- return statements must match the enclosing function result type;
- conditions in `if`, `if-else`, and `while` must be boolean;
- expression statements must have type `void`;
- assignments, declarations with initializers, and function-call arguments
  must match exactly, with no implicit casts;
- `++`, `--`, `%`, and array indices require `int`;
- arithmetic operands must be numeric scalars of the same type;
- ordering comparisons require `int` or `double`;
- equality comparisons are supported for non-array, non-void scalar values;
- array indexing requires an array expression and returns the element type;
- `.length` is only supported on arrays and has type `int`;
- foreach loops require an array expression and a loop variable type matching
  the element type.

Uninitialized scalar variables are given Javalette default values: `0`,
`0.0`, or `false`. Uninitialized array variables are initialized to an empty
array value of the corresponding array type.

## LLVM backend

The LLVM backend emits straightforward, unoptimized LLVM IR:

- local variables and parameters are represented with `alloca`, `load`, and
  `store`;
- integers are `i32`, doubles are `double`, booleans are `i1`, and strings are
  `i8*`;
- user functions are emitted as LLVM functions with matching parameter and
  result types;
- primitive I/O functions are emitted as external declarations;
- string literals are emitted as private global constants;
- short-circuit `&&` and `||` are emitted with branches and `phi` nodes;
- arrays are heap-allocated with `calloc`;
- each array value is a pointer to a structure containing a 32-bit length
  followed by a flexible element area;
- multidimensional arrays are represented as arrays of array pointers, and
  `new int[n][m]` allocates the outer array and each inner array;
- no array bounds checks are generated.

The output is intended to be linked with the provided runtime implementation
for the primitive I/O functions.

## RISC-V backend

The RISC-V backend emits RV64 assembly:

- integer and boolean values use integer registers and stack slots;
- doubles use floating-point registers and 8-byte stack slots;
- arrays and strings are represented as pointers;
- calls follow the standard RISC-V calling convention for integer and
  floating-point arguments, including stack-passed overflow arguments;
- local variables live in the stack frame;
- string and double constants are emitted in read-only data sections;
- arrays are allocated with `calloc` and use the same logical layout as the
  LLVM backend: length at offset 0 and elements after the header;
- multidimensional array creation recursively allocates nested arrays;
- primitive I/O is provided by `lib/runtime-riscv.s`.

This backend is not part of the original LLVM-only base assignment. It is an
additional native-code path for RV64 systems with the required cross toolchain.

## Parser conflicts

Bison reports two shift/reduce conflicts for the generated parser:

- Dangling `else`: in nested conditionals such as
  `if (a) if (b) s1 else s2`, Bison shifts `else`, so the `else` belongs to
  the nearest unmatched `if`. This is the conventional Javalette/C/Java
  interpretation.
- Array creation versus indexing after `new`: after parsing
  `new int[n]` and seeing another `[`, Bison shifts. Therefore
  `new int[n][m]` is parsed as multidimensional array creation, not as
  indexing the newly created one-dimensional array. To index a newly created
  array explicitly, write `(new int[n])[i]`.

There are no reduce/reduce conflicts.

## Implemented extensions

The compiler implements the array extensions:

- one-dimensional arrays;
- multidimensional arrays;
- array creation with one or more dimensions;
- array indexing and indexed assignment;
- array `.length`;
- foreach loops over arrays;
- arrays as function arguments and return values.

The compiler also contains an additional RV64 RISC-V backend and runtime
support.

## Not implemented

The following optional extensions from the course project are not implemented:

- structs and dynamic data structures;
- objects and dynamic dispatch;
- higher-order functions;
- generators;
- exception handling;
- garbage collection;
- native x86 or x86-64 code generation.

Array bounds checking is not generated. This is allowed by the array extension
description.
